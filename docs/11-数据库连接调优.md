# 11 · 数据库连接调优(RTT 量化 / 连接模式评估 / 本地 Docker 开发路径)

> 来源:DEV-29。业主本地测试反馈"页面查询与提交普遍缓慢",本文量化定位原因、
> 对比三种连接模式、给出本地零延迟开发路径与推荐配置,并附高频接口 N+1 抽查结论。
> 关联实现:`server/scripts/measure_db_latency.py`(测量脚本)、根目录
> `docker-compose.yml`(本地 PostgreSQL/MinIO)、`server/app/common/db/engine.py`
> (连接池策略开关)、`server/README.md` §4.2。

---

## 0. 结论摘要

1. **主因是地理延迟**:`.env` 指向 Supabase 新加坡区域 transaction pooler
   (`aws-1-ap-southeast-1.pooler.supabase.com:6543`),业主在中国大陆访问,
   单程 RTT 约 70~150ms。一个页面请求在后端串行执行 N 条 SQL 时,延迟按
   `N × RTT` 叠加(见 §4 实测:审核通过接口约 8~9 个串行往返,仅网络开销即
   0.6~1.4s)。
2. **次因是 transaction pooler + NullPool**:6543 事务模式下 asyncpg 预编译语句
   不可用,引擎强制 `NullPool`——每次取连接都要完整走一遍 TCP + TLS + 认证
   (比复用连接多 2~3 个 RTT,见 §1.3)。这在远程高 RTT 链路上被放大。
3. **本地开发最有效的解法是本地 Docker PostgreSQL**(§3):延迟从 ~100ms 级降到
   <1ms,且空库 `alembic upgrade head` 一次跑通(DEV-13 已固化静态迁移基线)。
   Supabase 保留给联调/共享数据场景。
4. **生产选型取决于部署区域**(未定,见 §5 前提):后端与数据库同区域时,
   常驻 FastAPI 建议会话模式 pooler(5432)或直连 + 应用侧连接池;后端若部署在
   中国大陆,任何连接模式都改不了跨境 RTT,应就近部署。
5. **N+1 抽查**(§6):发现 1 处真 N+1(赛季历史统计)、1 处小规模 N+1
   (家庭成员列表)、以及普遍的"commit 后 refresh"额外往返模式;均**仅记录**,
   本期不改行为语义。

## 1. 量化测量方法(可照抄)

### 1.1 网络层:到 pooler 的 RTT

ICMP ping 可能被防火墙吞(Windows 报 "Error due to lack of resources" 或全部
超时),所以测量脚本同时提供 **TCP 握手探测**(不需要数据库凭据):

```powershell
# 方式 A:ICMP(通就用它)
Test-Connection aws-1-ap-southeast-1.pooler.supabase.com -Count 50 |
  Measure-Object ResponseTime -Average -Minimum -Maximum

# 方式 B:TCP 握手 + 完整链路(推荐,一条命令三层全测)
cd server
uv run python scripts/measure_db_latency.py --rounds 50
```

`measure_db_latency.py` 输出三行分布(min / p50 / p90 / max / avg,毫秒):

| 测项 | 含义 | 区分什么 |
|---|---|---|
| TCP 握手 host:port | 建立 TCP 连接耗时 | 纯网络 RTT(下界) |
| 复用连接 select 1 | 常驻连接上反复 `select 1` | 查询本身 + 1×RTT |
| 逐次新建连接 select 1 | 每轮 connect→select 1→close | 连接建立(TLS+认证)+ 查询;即 NullPool 在 6543 下的逐操作真实开销 |

读的是 `server/config.yaml` + `.env` 拼出的连接配置(与 `app/common/db/engine.py`
同源),测的就是应用实际走的链路。**对比 6543 / 5432**:改 `.env` 的
`DATABASE_HOST`/`DATABASE_PORT` 后各跑一遍即可。

### 1.2 会话模式 pooler(5432)怎么测

`.env` 只改端口,host 不变(同一台 pooler 机器):

```ini
DATABASE_HOST=aws-1-ap-southeast-1.pooler.supabase.com
DATABASE_PORT=5432          # 6543 → 5432,其余不动
```

### 1.3 参考实测数据

**测量点 A:agent 运行机(2026-10-11,非中国大陆出口,仅作基线参照)**,
TCP 握手各 15 轮(业主环境数字会明显更高,请以本地实测为准):

| 目标 | n | min | p50 | p90 | max | avg |
|---|---|---|---|---|---|---|
| pooler:6543(事务,现状) | 15 | 1ms | 16ms | 18ms | 67ms | 18ms |
| pooler:5432(会话) | 15 | 1ms | 18ms | 25ms | 26ms | 17ms |

两个端口同机同网络路径,RTT 无差别——**换连接模式不会降低网络延迟**,
降低的是每操作附加的连接建立开销与每查询的预编译/往返开销。

**测量点 B:业主本地(中国大陆,待补)**——请在本机执行:

```powershell
cd server
# .env 指向 6543 时跑一次,改成 5432 后再跑一次,把两份输出贴到下表
uv run python scripts/measure_db_latency.py --rounds 50
```

| 测项 | 6543(事务) | 5432(会话) |
|---|---|---|
| TCP 握手 p50/p90 | 待补 | 待补 |
| 复用连接 select 1 p50/p90 | 待补 | 待补 |
| 逐次新建连接 select 1 p50/p90 | 待补 | 待补 |

**解读口径**:
- `复用 select 1 ≈ 1×RTT + 查询耗时(亚毫秒)` —— 它减去 TCP 握手就是纯查询成本;
- `逐次新建 − 复用 ≈ 连接建立开销(2~3×RTT:TCP + TLS + 认证)` —— 这就是
  NullPool 在高 RTT 链路上的额外代价,也是"同样的 SQL,本地快远程慢"的主要放大器之一。

## 2. 三种连接模式对比

| 维度 | ① 事务模式 pooler(6543,现状) | ② 会话模式 pooler(5432,同一 pooler 域名) | ③ 直连(db.\<ref\>.supabase.co:5432) |
|---|---|---|---|
| 连接语义 | 每个事务可能落到不同后端连接 | 一个客户端连接独占一个后端连接,连接存活期间绑定 | 客户端直连数据库进程 |
| asyncpg 预编译语句 | ❌(报 `prepared statement ... already exists`) | ✅ | ✅ |
| 应用侧连接池 | ❌ 必须 NullPool(事务间不能持有会话状态) | ✅ 推荐(否则每个客户端连接钉死一个后端连接) | ✅ 推荐 |
| 每查询额外开销 | 事务路由 + 无语句缓存(每次完整 parse) | 语句缓存生效,池化连接复用 | 同左,且少一跳 pooler |
| 每操作连接建立 | NullPool 逐操作新建(TCP+TLS+认证 ≈ 2~3×RTT) | 池化后只在冷启动/回收时新建 | 同左 |
| 服务端连接占用 | 只占事务持续时间,**并发承载最高** | 每个客户端连接占一个后端连接(受套餐上限约束) | 同左,且直连有独立配额 |
| 网络路径 | pooler 域名(新加坡) | 同一 pooler 域名,**RTT 与 ① 相同** | 直连数据库域名(**仅 IPv6**,IPv4 需付费 add-on) |
| 常驻 FastAPI 适用性 | 可用但浪费(为 serverless 场景设计的模式) | **适合** | 适合(IPv6 可达为前提) |
| 典型场景 | Serverless/边缘函数、短事务高并发 | 常驻后端 + 中低并发 | 常驻后端、需要长连接/特殊扩展 |

**结论**:
- **本地开发**:不值得在 ①②③ 里挑——直接上本地 Docker PostgreSQL(§3),
  RTT≈0,预编译语句与连接池全部生效(`DATABASE_POOL_MODE` 默认 `auto`,
  非 6543 端口自动恢复默认连接池,无需额外配置)。
- **联调/共享数据(仍用 Supabase)**:常驻后端从 6543 切到 **② 会话模式 5432**,
  一行 `.env` 改动(host 不变),恢复语句缓存 + 应用侧连接池;高 RTT 下每操作
  省 2~3×RTT 连接建立开销。注意会话模式占后端连接配额,并发很低的本地/联调
  场景完全无压力。
- **`pool_pre_ping` 的权衡**:默认池模式下 `pool_pre_ping=true` 会在每次从池里取
  连接时多发一个 `select 1` 预检(+1 RTT)。本地 Docker(<1ms)无感;大陆联调
  5432(高 RTT)若想再省这一跳,可在 `config.yaml` 的 `database.pool` 下把
  `pool_pre_ping` 置 `false`——代价是池中已被服务端断开的陈旧连接会在第一个真实
  查询上报错(由 `pool_recycle=3600` 定期回收兜底),连接稳定的本地/联调库可接受。
- **生产**:见 §5,结论带前提(部署区域未定)。

## 3. 本地 Docker PostgreSQL 开发路径(重点)

本地库延迟接近零(<1ms),日常开发/自测/跑测试都不再吃跨境 RTT。Supabase 保留
给联调与多人共享数据场景。

### 3.1 起库(仓库根目录)

```bash
# 仅 PostgreSQL
docker compose up -d

# 需要对象存储联调时连 MinIO 一起
docker compose --profile storage up -d
```

`docker-compose.yml`(仓库根)提供 `postgres:16-alpine`(库名 `life_online`,
UTF8,与生产编码一致)+ 可选 MinIO(9000 API / 9001 控制台,默认 minioadmin)。
数据落在命名卷 `life_online_pgdata`,`docker compose down` 不丢;彻底重来用
`docker compose down -v`。

### 3.2 `.env` 本地配置

把 Supabase 段注释掉,换成本地块(`server/.env.example` 已内置同款注释模板):

```ini
DATABASE_HOST=127.0.0.1
DATABASE_PORT=5432
DATABASE_USER=postgres
DATABASE_PASSWORD=postgres
DATABASE_NAME=life_online
DATABASE_SSLMODE=disable
# DATABASE_POOL_MODE 留空即可:非 6543 端口自动恢复默认连接池 + 语句缓存

# 对象存储用本地文件模式即可(不需要 MinIO)
STORAGE_PROVIDER=local
```

### 3.3 建库(空库一次跑通)

```bash
cd server
uv sync                       # 首次
uv run alembic upgrade head   # 空库 → 完整 schema(静态迁移基线,DEV-13 固化)
```

### 3.4 校验 schema 与模型零差异

```bash
uv run python scripts/diff_pg_schema.py    # 无差异退出码 0;有差异逐项列出并退出 1
```

### 3.5 验证延迟(可选)

```bash
uv run python scripts/measure_db_latency.py --rounds 30
# 本地预期:TCP 握手与 select 1 都在个位数毫秒以内
```

### 3.6 造数据 / 登录

```bash
uv run python scripts/seed_dev_data.py     # 最小家庭数据链路
# .env 置 DEV_LOGIN_ENABLED=true 后可用 POST /api/v1/sys/auth/dev-login 直接换 token
```

### 3.7 切回 Supabase 联调

把 `.env` 数据库段换回 Supabase(6543 或 5432)即可,代码零改动;两套库的
schema 都可随时用 `diff_pg_schema.py` 对齐校验。

## 4. 高频接口 N+1 / 分页抽查(仅记录,本期不改)

抽查范围:任务列表、提交、审核、时间币流水、赛季列表/历史、家庭成员、`/me`。
**代码未做任何修改**,以下为发现清单与后续建议(按影响排序):

| # | 位置 | 问题 | 影响 | 后续建议(不在本期) |
|---|---|---|---|---|
| 1 | `server/app/services/season_service.py:91` `season_history` | **真 N+1**:先查全部赛季,再逐赛季 `select(ScnTaskInstance)` 拉该赛季**全部任务实例**到内存统计(非聚合 SQL) | 赛季 × 每季任务全量行数,数据增长后最重;`GET /scn/seasons/history` | 改一条 `GROUP BY season_id` 聚合(`count` + `count case status` + `sum(xp_awarded)`) |
| 2 | `server/app/api/v1/families.py:31` `_account_to_read` | 小规模 N+1:成员列表循环内逐个查 `SysChild` | 每个孩子成员 +1 查询;家庭规模小(≤个位数),影响有限 | 一次 `IN` 查询预取,或 `selectinload` |
| 3 | `task_service` 各写操作(`submit/approve/reject/abandon`) | 模式问题:`await db.commit()` 后紧跟 `db.refresh(...)`(approve 还有 `refresh(assignee)`),每次 refresh = 1 个额外 RTT | 审核通过全链路约 **8~9 个串行往返**(get_task 含 selectinload 2 + ensure_child 1 + 特权解锁 2 + commit 1 + refresh×2 + 认证 load_user 1);100ms RTT 下仅网络即 ~0.8s | 利用 `expire_on_commit=False` 下已加载状态直接返回,或 `RETURNING`;收益与 RTT 成正比 |
| 4 | `server/app/api/v1/users.py:52` `get_me` | 每日重置路径:reset + commit + `refresh(child)` + `refresh(user)`,且 `_to_read` 再查一次 child(同一请求内查两遍) | 仅孩子每天首次调用触发,影响一次性 | reset 分支复用已加载的 child 对象 |
| 5 | 列表接口 count 查询 | 任务列表/时间币流水每次列表 = 数据查询 + `count(*)` 两次往返 | 每次列表 +1 RTT | 可选:keyset 分页或"首页不返回精确 total";低优先 |
| 6 | 认证链路 `load_user` | 每个受保护请求 1 次 `db.get(SysAccount)` | 每请求固定 +1 RTT | 正常设计,保持;真要省可加短 TTL 缓存,涉及语义,不做 |

**分页结论**:任务列表 ✅(page/page_size ≤200 + total)、时间币流水 ✅ 同款分页;
赛季列表/历史**无分页**(单家庭赛季数为个位数,可接受,记录在案)。
`list_tasks` 的 `selectinload(template)` 是整页一次预取(2 条 SQL),**不是** N+1。

## 5. 推荐配置与生产选型(前提:部署区域未定)

### 5.1 三套推荐配置

| 场景 | 连接 | `.env` 关键项 | 连接池策略 |
|---|---|---|---|
| **本地开发(推荐日常)** | Docker PostgreSQL | `127.0.0.1:5432`,`DATABASE_SSLMODE=disable` | `auto` → 默认池 + 语句缓存 |
| **联调/共享数据** | Supabase 会话模式 pooler | pooler 域名 + `DATABASE_PORT=5432` | `auto` → 默认池 + 语句缓存 |
| **兼容现状** | Supabase 事务模式 pooler | pooler 域名 + `DATABASE_PORT=6543`(现状) | `auto` → NullPool + 无语句缓存(行为与 DEV-29 之前完全一致) |

### 5.2 生产选型(⚠️ 结论依赖"后端部署区域"这一前提)

- **前提 A:后端与 Supabase 同区域部署**(如 ap-southeast-1):
  RTT <5ms,连接模式差异被网络摊平。常驻 FastAPI(当前 `workers: 1`、低并发)
  建议**会话模式 pooler(5432)+ 应用侧连接池**——语句缓存与连接复用生效,
  占用少量后端连接配额完全可接受;若未来出现多实例/高并发/弹性伸缩,再回退
  事务模式 6543(并发承载最高、不占后端连接)。
- **前提 B:后端部署在中国大陆**:跨境 RTT(70~200ms 且抖动)是主导因素,
  **换任何连接模式都无效**。应就近部署(后端与数据库同区域),或改用大陆境内
  数据库;届时连接模式再按前提 A 评估。
- IPv6 注意:直连 `db.<ref>.supabase.co` 仅 IPv6,IPv4 需 Supabase 付费
  IPv4 add-on;无特殊需求用 pooler 域名即可。

### 5.3 慢查询日志开关(评估,后续项,本期不实现)

建议做成应用层配置(部署环境无关,Supabase/本地/自托管通用):

- `config.yaml` 新增 `database.slow_query_log_ms`,默认 `0`(**关闭**,零开销零噪音);
- SQLAlchemy `before_cursor_execute` / `after_cursor_execute` 事件对超过阈值的
  语句打结构化日志(耗时 + 截断的语句头 + request id),接入现有
  `app/common/logging.py`;
- 替代方案:PG 侧 `log_min_duration_statement`(Supabase 需在控制台/角色级设置,
  日志在 Dashboard → Logs,不依赖应用发版,但阈值全局生效、无法按环境灰度)。
- 优先级:低于 §4 的 N+1 修复;建议与 N+1 修复同期做,用它验收修复效果。
