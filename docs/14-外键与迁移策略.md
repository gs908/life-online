## 0. 结论摘要

1. **保留数据库级外键**。全部 72 个 FK(42 CASCADE / 30 SET NULL;合并 DEV-33/36 的触发/协作表后复核)维持现状,
   不改为程序层维护(否决论证见 §1.2)。没有任何 FK 语义调整,本期**不产出 Alembic 迁移**。
2. **不引入 `DEFERRABLE INITIALLY DEFERRED`**(§3.1)。当前唯一的表间环
   (`sys_child → scn_onboarding_step → scn_task_template → sys_child`)环边全部可空,
   用"置 NULL + 回填"即可走通导入;deferrable 的代价(SQLAlchemy 不建模、diff 脚本不可见、
   错误延迟到 COMMIT)大于收益。给出了未来改用 deferrable 的明确触发条件。
3. **不使用 `SET session_replication_role = replica` / `pg_dump --disable-triggers`**。
   两者都要求 superuser;Supabase 的 `postgres` 角色不是 superuser,实测非超用户
   `permission denied to set parameter "session_replication_role"`(§3.2,含官方文档引用与复现命令)。
4. **批量导入统一走拓扑顺序**(§3.3):新增 `scripts/fk_topo_order.py`,输出
   导入顺序 / 删除顺序 / 分层视图,自动识别循环引用并给出"回填边"。
   当前模型:29 张表、6 层、1 条回填边(`sys_child.onboarding_step_id`)。
5. **ondelete 语义复核结论(§4)**:42 CASCADE / 30 SET NULL 逐组核对,与业务语义一致,
   无需调整项。家庭级联删除波及全部 22 张业务表,属"数据主体清除"语义,保留;
   时间币流水、行为轨迹在任务/赛季删除路径下均因 SET NULL 存活,审计数据不会被误删。
   两条应用层守卫建议**仅记录不改**(§4.3)。
6. **软删除策略(§5)**:不统一给审计表加 `deleted_at`。流水/轨迹是 append-only 事件,
   正确做法是"没有删除路径"而非"软删除"——现状已满足。`scn_task_proof.deleted_at`
   保留用于审核驳回;家庭/孩子级物理级联作为数据清除的唯一出口,运维级执行。

## 1. 决策:保留数据库级外键

### 1.1 依据

1. **ORM 已经依赖 DB 级联**。模型 relationships 普遍配置 `passive_deletes=True`
   (`sys_family` / `sys_account` / `scn_season` / `scn_onboarding_path` 等),
   即删除时**不加载子对象进内存**,直接交给数据库 FK CASCADE。去掉 DB FK 后,
   这些 relationship 要么静默失效(留下孤儿行),要么改回默认行为(N+1 全量加载后逐行删)。
2. **写入方不止应用**。本项目存在多个直连数据库的入口:多 agent 协作、
   `scripts/sync_postgres_schema.py`、运维手工改数、未来的 ETL 导入。
   应用层校验只覆盖 FastAPI 一条路,其余路径全部裸奔。数据完整性约束放在数据库层,
   是唯一对所有写入方生效的位置。
3. **并发安全**。应用层"先查后插"式的引用校验在并发下有 check-then-act 竞态,
   DB FK 是最终防线;删掉它等于要求所有引用校验都加锁,复杂度转嫁给每个写入方。
4. **迁移出问题的真实风险不在 FK 本身,而在导入顺序**(业主的原始担忧)。
   这正是 §3 用拓扑顺序脚本解决的:29 张表 6 层 + 1 条回填边,
   按清单执行即可,不需要拆掉完整性约束来换导入便利。
5. **72 个 FK 的运行期开销在本项目规模下可忽略**。每张表数据量在家庭级应用
   (万行级)远够不着"批量导入性能墙";级联删除路径上的外键列均已建索引
   (`index=True`),级联删除走索引,不产生全表扫描(个别 SET NULL 列如
   `creator_account_id` 未建索引,不在删除路径上,不影响本决策)。

### 1.2 否决论证:程序层维护外键(数据库不建 FK)

| 该方案的声称收益 | 实际情况 |
|---|---|
| 批量导入更方便(不用管顺序) | 假收益。拓扑顺序脚本一条命令输出顺序(§3.3);而"方便"的代价是**任何时刻**引用完整性都不受保护,不只是导入那一刻 |
| 删除/更新更灵活 | 实为风险。没有 FK 约束的"灵活删除"正是孤儿数据、账实不符的来源;本项目 `passive_deletes=True` 的级联行为会静默失效 |
| schema 演进不被约束拖累 | 演进由 Alembic 管理,与 FK 存废无关;相反,FK 是 `diff_pg_schema.py` 做实库比对的一部分,去掉后比对覆盖面变小 |
| 应用层校验足够 | 不成立。见 §1.1 第 2、3 条:脚本/手工/并发路径全部绕过应用层 |

**结论:程序层维护 FK 的方案否决。** 引用完整性是数据资产属性,不是应用功能属性;
功能可以分批上线,完整性必须从头到尾只有一个权威执行点——数据库。

## 2. 现状盘点(merge origin/develop 后 HEAD 实测)

- 72 个 `ForeignKey`:`ondelete="CASCADE"` 42 个、`ondelete="SET NULL"` 30 个,
  与程序化扫描 `Base.metadata` 的结果一致(逐表清单见 §4 附录)。
- **2 处 `use_alter=True`**:`sys_child.onboarding_path_id` / `onboarding_step_id`
  → onboarding 两表。其中**真正在环上的只有 `onboarding_step_id`**:模型存在一个
  **真实的表间环** `sys_child → scn_onboarding_step → scn_task_template → sys_child`
  (孩子引用引导步骤,步骤引用任务模板,模板又可指定目标孩子);
  `onboarding_path_id` 与环无关,其 `use_alter` 是历史遗留的冗余声明(模型层既有
  现象,非本文档引入,无行为影响,仅记录不改)。`use_alter` 把约束改为建表后
  `ALTER TABLE` 补建,解决的是 **DDL** 破环;**数据导入**的破环见 §3.3 的"回填边"。
- 无任何 `deferrable` 约束;此前无文档化的迁移/导入策略(本文即补此缺)。

## 3. 迁移 / 批量导入方案裁决

三条候选路径,结论:**拓扑顺序采用,deferrable 与 replica 模式否决**。

### 3.1 `DEFERRABLE INITIALLY DEFERRED` —— 否决(附启用条件)

收益:单事务内可乱序写入(校验延迟到 COMMIT),环上表导入不用置 NULL 回填。

否决理由(代价 > 收益):
1. **SQLAlchemy 的 `ForeignKey` 不建模 deferrable 语义**,`diff_pg_schema.py` 目前
   比对"引用/ondelete"但不比对 deferrability——改了之后**实库漂移对现有工具不可见**,
   需要同步增强比对脚本,引入持续的维护成本。
2. **错误定位后移**:violation 从"哪条 INSERT"变成"COMMIT 时刻",应用侧排障变难;
   本项目业务写入(服务层)都是小事务、天然按依赖顺序,得不到任何收益。
3. **改约束本身要 `DROP CONSTRAINT` + `ADD CONSTRAINT ... DEFERRABLE`**,
   全程 ACCESS EXCLUSIVE 锁;对 Supabase 实库是一次纯粹的风险敞口,换不来当下收益。
4. 唯一真实的收益场景(环上表大批量导入)已被"置 NULL + 回填"覆盖(§3.3),
   且当前环边全部可空,方案走得通。

**未来启用 deferrable 的触发条件**(满足其一再议,届时出 Alembic 迁移并同步增强 diff 脚本):
- 模型出现**不可空**的循环引用(`fk_topo_order.py` 会明确报错提示);
- 出现高频(周级以上)的跨表大批量重导入需求,且实测回填方案成为瓶颈。

### 3.2 `session_replication_role = replica` / `pg_dump --disable-triggers` —— 否决

权限事实:
- PostgreSQL 官方文档(runtime-config-client):`session_replication_role`
  *"Only superusers and users with the appropriate `SET` privilege can change this setting"*;
  且 *"setting this parameter to `replica` also disables all foreign key checks,
  which can leave data in an inconsistent state if improperly used"*。
- PostgreSQL 官方文档(app-pgdump):`--disable-triggers`
  *"Presently, the commands emitted for `--disable-triggers` must be done as superuser."*
- Supabase 官方 roles 文档:`postgres` 角色是 *"admin privileges"* 角色,**不是 superuser**
  (superuser `supabase_admin` 平台保留,用户拿不到)。

本地实测复现(PG 17.11,非超用户角色):

```text
=# set role dev31_tmp_nosuper;   -- 非超用户
=> set session_replication_role = replica;
ERROR:  permission denied to set parameter "session_replication_role"
```

结论:**在 Supabase postgres 角色下这两条路都走不通**;本地 `gs_dev` 是 superuser
虽然能跑,但规范上统一禁用——`replica` 模式连 FK 校验一起关掉,导入中途出错会留下
静默的坏引用,与"保留 DB FK"的决策自相矛盾。需要绕过顺序约束的场景一律用 §3.3。

> 注:整库迁移(建表 + 数据一起)走 `pg_dump -Fc` + `pg_restore` **不需要**上述手段,
> pg_restore 自己按依赖处理约束与数据(见 §4.4 README)。

### 3.3 拓扑顺序导入 —— 采用(本期落地)

新增 `server/scripts/fk_topo_order.py`(只读 `Base.metadata`,不连库、不读配置):

```bash
cd server
uv run python scripts/fk_topo_order.py             # 正向:导入顺序 + 回填边提示
uv run python scripts/fk_topo_order.py --reverse   # 逆向:DELETE/TRUNCATE 顺序
uv run python scripts/fk_topo_order.py --layers    # 分层视图(同层可并行)
```

当前输出概要:29 张表、6 层;自动识别出 §2 的表间环,回填边取环上的 `use_alter` 外键
(DDL 破环边即数据导入破环边,语义一致):

```
# 循环引用回填边(导入时先置 NULL,全部导入完成后回填):
#   UPDATE sys_child SET onboarding_step_id = ...
```

若未来出现不可空环,脚本直接报错并提示走 §3.1 的 deferrable 触发条件,
不会输出错误顺序。单测:`tests/test_fk_topo_order.py`(顺序合法性、回填边选择、
不可空环报错),`uv run pytest tests/test_fk_topo_order.py` 全绿。

与现有脚本配套的完整导入步骤(可照抄版)见 `server/README.md` §4.4:
`sync_postgres_schema.py`(空库建表)→ `fk_topo_order.py`(拿顺序)→ 导入 + 回填 →
`diff_pg_schema.py`(终检)。

## 4. ondelete 语义复核

### 4.1 家庭级联删除的波及面

FK 指向 `sys_family` 且 `CASCADE` 的共 **22 张表**——即删除一个家庭会物理清除:
账号、孩子、赛季、任务模板/实例、证明、时间币(余额+流水)、时间配置、特权(模板/解锁/使用)、
新手引导、通知、统计、轨迹、上传记录、邀请。**当前没有任何 API 暴露家庭删除**,
唯一触发路径是运维级数据库操作。

**裁决:保留,不调整。** 家庭是本系统的顶层隔离单元,家庭级删除的语义就是
"数据主体清除"(类比 GDPR erasure):此时**应该**删干净,包括流水。
把它改成软删除/SET NULL 反而留下无法解释的孤儿账本。

### 4.2 审计类数据误删核查(重点)

| 审计/历史数据 | 删除路径下的行为 | 结论 |
|---|---|---|
| 时间币流水 `scn_time_coin_log` | `task_instance_id` / `season_id` 均 SET NULL;删任务/删赛季**不**波及流水 | ✅ 不会误删 |
| 行为轨迹 `scn_trace` | `season_id` / `actor_account_id` / `child_id` 均 SET NULL | ✅ 不会误删 |
| 任务证明 `scn_task_proof` | `task_instance_id` CASCADE:删任务实例物理删证明 | ⚠️ 见 §4.3-2,语义成立但需应用层守卫 |
| 邀请历史 `sys_invite` | `used_by` / `created_by` SET NULL,邀请记录保留 | ✅ |

### 4.3 需调整清单

**FK 语义(ondelete)调整:无。** 39/29 逐组核对与业务语义一致,典型模式:
- "配置/主体随家庭走" → CASCADE(账号、孩子、模板、配置);
- "历史事实要存活" → SET NULL(流水对任务/赛季、轨迹对操作者、邀请对使用者);
- 账号删除 → 登录渠道 CASCADE(凭证随账号)、创作内容 SET NULL(模板保留、`creator_account_id` 置空)。

**应用层守卫建议(仅记录,不改变默认语义,待业主/产品确认后另开任务):**
1. `season_service.delete_season` 未守卫"赛季下仍有任务":父母删赛季会级联清除该赛季
   全部任务实例与证明。建议删除前检查并要求显式确认(历史面板依赖赛季数据)。
2. `task_service.delete_task` 物理级联删除 `scn_task_proof` 行,但 MinIO 对象不会随之清理,
   与 `sys_upload`(SET NULL 存活)不一致。建议:有证明的任务拒绝物理删除,
   或删除时同步清理对象存储。

## 5. 软删除策略

现状:`scn_task_proof` 是唯一带 `deleted_at` 的表(审核驳回场景)。

**结论:不统一给审计/历史表加 `deleted_at`。** 理由与口径:

1. **流水、轨迹是 append-only 事件**,业务上没有"撤回一条流水"的操作;
   它们需要的保护是"**不存在删除路径**",而不是"删了留痕"。复核确认(§4.2)
   常规删除路径(任务/赛季/主题)确实不触及这两类表——现状已满足,加 `deleted_at`
   是没有写入方的列。
2. **唯一物理级联出口 = 家庭/孩子删除**(数据主体清除),该语义下就应删净,不软删。
3. `scn_task_proof.deleted_at` 保留:证明是"内容"而非"事件",驳回/替换有业务语义。
4. 新增表时的判定口径:**事件类(流水/轨迹/通知)不加软删除,靠 SET NULL + 无删除路径保护;
   内容类(证明/模板)可加,删除走软删。**
