## 1. 块 A:任务触发与实例生成(Q1 + Q3)

### 1.1 实现形态(目标声明)

模板可挂**多组触发规则**(每日 / 指定星期 / 每月某日 / cron 表达式 / 一次性),调度器按规则**幂等生成实例**;
日常任务"每天/指定天"各生成一条,挑战任务按"每周/每月/cron"周期生成,限时任务额外带**时间窗**(截止时间,或开始时间+有效时长);
**每个模板同时最多 1 条未消费实例(D1)**。

### 1.3 生成算法(幂等 + 多触发去重)

新服务 `app/services/task_generator_service.py`:

```
due_templates(today, now):
    任一 active trigger 命中(DAILY/WEEKDAYS/MONTHLY/CRON 匹配 today,
    generate_at 已过,日期在 [starts_on, ends_on])

for t in due_templates:
    open_ = 最近一条 instance where template_id=t.id
            and status in (AVAILABLE, IN_PROGRESS, PENDING_REVIEW)  # 未消费
    if open_ is None:
        create_instance(t, generated_for_date=today, expire_at=compute_expire_at(t, today))
    elif open_.status == AVAILABLE and t.pool_policy == REUSE_UNTIL_CONSUMED:
        roll_forward(open_, today)          # 未消费 → 顺延(见 1.4)
    else:
        pass                                # IN_PROGRESS / PENDING_REVIEW:进行中,不再生成
# 唯一索引兜底并发;IntegrityError → 取回既有 (template_id, today) 行
```

- **多组触发**:同一模板可并存"工作日 07:00 + 周末 09:00";同日多规则命中也只生成 1 条(按模板去重)。
- **类型默认规则**:DAILY→`DAILY`/`WEEKDAYS`;CHALLENGE→`WEEKLY`/`MONTHLY`/`CRON`;TIMED→触发规则负责"何时生成",时间窗负责"何时截止";一次性→`ONCE`。
- **立即生成**:模板创建 / 改规则 / 激活后,同步对该模板跑一次生成(孩子端当场可见)。

`compute_expire_at(t, day)`:`NONE`→`NULL`;`DEADLINE`→`day @ deadline_time`;`DURATION`→`day @ (start_time + duration_minutes)`。

### 1.4 顺延(roll_forward)的目的与机制

**目的(D1)**:让未消费实例在跨天后**依然有效,并作为备选显示在孩子端任务列表**——即"未消费自动顺延,显示为备选"。

两层机制:
1. **业务层**:生成器见"存在未消费实例"即跳过生成 → 同一模板不重复出条。
2. **数据层**:`roll_forward` 把该实例 `generated_for_date` 前移到今天、按今天窗口重算 `expire_at`(限时任务)。
   这样它不被过期 job 误杀、日期显示为当前,且唯一索引把"同日再生成"堵死。

不做前滚的后果:实例带旧窗口被判 EXPIRED 消失,或同日重复生成。

`pool_policy`(D1 默认 `REUSE_UNTIL_CONSUMED`):
- `REUSE_UNTIL_CONSUMED`(默认):未消费一直顺延,不新增。
- `NEW_EACH_PERIOD`(备选,本轮不默认):每周期照常出新,旧的未消费实例置"过期未完成"保留历史。

## 2. 块 B:消费 / 未消费语义(D2)

### 2.1 实现形态(目标声明)

**领取且提交完成(COMPLETED)= 已消费**;**退回 / 未完成 = 未消费**,未消费实例自动顺延继续挂在列表。

### 2.2 规则表

| 状态 | 是否已消费 | 生成器动作 |
|---|---|---|
| AVAILABLE(未接取) | 否 | 顺延 |
| IN_PROGRESS(接了未交) | 否 | 保持,不新增(进行中) |
| PENDING_REVIEW(交了待审) | 否 | 保持,不新增 |
| reject → IN_PROGRESS(驳回退回) | 否 | 保持,不新增 |
| abandon → AVAILABLE | 否 | 顺延 |
| COMPLETED | **是** | 下个触发周期生成新实例 |
| EXPIRED | 否(周期已终结) | **不顺延**,下个周期生成新实例 |

> 同一模板"未提交"时不再生成 → 并行度恒为 1;"日常任务多条"来自多模板 + 每周期消费后重生。

## 3. 块 C:押金 = 耗时驱动;难度 → XP(D3 / Q4)

### 3.1 实现形态(目标声明)

押金**主要按预计耗时**计算,并受类型区间与"≤当日配额×比例"约束;难度**不进押金**,改为**影响获得的经验值**。

### 3.2 押金计算(`coin_service.resolve_deposit`)

```python
# app/config.py 新增 DepositSection
reference_minutes = 30
by_type = {  # (default, min, max)
  DAILY:(10,5,20), CHALLENGE:(30,15,50), CHAIN:(20,10,30),
  TIMED:(25,15,40), COOP:(5,0,20), HIDDEN:(0,0,0),
}
allowance_cap_ratio = 0.5
timeout_refund_ratio = 0.5          # 见块 D
abandon_full_refund_limit = 3       # 从 coin_service 魔数挪入
abandon_penalty_refund_ratio = 0.6
```

```python
async def resolve_deposit(db, *, template_type, estimated_minutes=None,
                          explicit=None, family_id) -> int:
    band = cfg.by_type[template_type]
    if explicit is not None:
        deposit = explicit
    elif estimated_minutes:
        f = clamp(estimated_minutes / cfg.reference_minutes, 0.5, 2.0)
        deposit = round(band.default * f)
    else:
        deposit = band.default
    deposit = clamp(deposit, band.min, band.max)
    deposit = min(deposit, floor(当日配额 * cfg.allowance_cap_ratio))
    return deposit
```

- 删除 `task_service.py:173/262/327/399` 的 `time_deposit or 10` 兜底;实例/模板创建时即解析落库。
- 例:30 分钟日常→10;60 分钟→20(DAILY 上限);15 分钟→5(下限)。
- 模板库套用时用 `suggested_time_deposit` 播种(现为死字段)。

### 3.3 难度 → XP

- `xp_service.calculate_xp` 增 `difficulty` 参数;配置 `difficulty_multiplier = {1:0.9, 2:1.0, 3:1.1, 4:1.25, 5:1.4}`。
- `approve_task` 传 `template.difficulty`,与既有 `rating`(家长评价,1-5 星)**相乘**。

### 3.4 前端 / 验证

- 管理端表单填"难度 + 预计耗时",实时显示后端算出的押金(可选 `POST /scn/task-templates/preview-deposit`)。
- 测试(`test_deposit_resolution.py`):各类型缺省、耗时 0.5x/1x/2x、显式越界、配额上限封顶、难度只改 XP 不改押金。

## 4. 块 D:执行中超时扣一半(D4 / 点 5)

### 4.1 实现形态(目标声明)

**已接取(IN_PROGRESS)** 的任务超过时间窗未提交 → 状态置 EXPIRED,**退还押金 50%、扣罚 50%**,并通知;
**未接取(AVAILABLE)** 超时 → 直接 EXPIRED,不涉及押金。

### 4.2 规则与落点

- 改造 `expire_overdue_tasks`(现 `task_service.py:396-409` 对 IN_PROGRESS 是**全额退**):
  - IN_PROGRESS 且 `timed_mode != NONE` → 退 `deposit * timeout_refund_ratio(0.5)` + 记罚 `deposit * 0.5`(走 `ABANDON_PENALTY` 或新增 `TIMEOUT_PENALTY`),状态 EXPIRED。
  - AVAILABLE → EXPIRED,无押金动作。
- 非限时任务 `expire_at = NULL`,不参与过期(走顺延,块 A)。
- 新增通知类型 `TASK_EXPIRED`(现 `NotificationType` 无超时项)。

### 4.3 文档对齐(必须)

`docs/06 §11` 现写 `AVAILABLE → EXPIRED 扣 50% 押金`(未接取无押金,语义矛盾),按 D4 统一为 **`IN_PROGRESS → EXPIRED 扣 50%`**,同步 `docs/04 §3.3`、`docs/07 A9`。

## 6. 块 F:CHAIN / COOP(D6 / 点 7)

### 6.1 实现形态(目标声明)

- **CHAIN(串行/递进)**:一个模板定义有序步骤,上一步 COMPLETED 才解锁下一步;**难度/耗时逐步上升**,链末给 XP 加成。
- **COOP(协作)**:一次任务可有多名参与者(多个孩子,或家长+孩子),押金与 XP 按参与者分摊。

> 原始需求文档(`D:\workspaces\documents\生活online\`)本机不存在,以下为按枚举注释 + `xp_service` 既有 `chain_index/chain_total/chain_final_bonus(1.5)` + `docs/04` 反推,已经评审确认按此实现(D6)。

### 6.2 CHAIN

- 模型:模板加 `chain_key`、`chain_order`、`chain_total`;实例加 `chain_index`、`chain_total`。
- 生成:触发时只投放链首步;第 N 步 COMPLETED 后生成第 N+1 步(顺延/池规则对链内步骤同样生效)。
- 递进:每步 `estimated_minutes` / `difficulty` 按步配置,形成"越来越难"。
- 奖励:`approve_task` 把 `chain_index/chain_total` 传入 `calculate_xp`,链末 ×`chain_final_bonus(1.5)`(配置已存在)。
- **中断与续做(已定稿)**:链内某步放弃(abandon)或超时,**不回退整条链**——已完成步骤保持 COMPLETED 不重置,当前未完成步骤按池规则顺延/可重做,下次从断点处继续。

### 6.3 COOP

- 模型:新增 `scn_task_participant(task_instance_id, account_id/child_id, role, confirmed_at)`;`assignee_child_id` 保留为主接取人。
- 形态:支持两类参与者角色——多孩子协作 / 亲子协作(家长作为一方参与者)。
- 押金:按 `docs/04`"分摊"(`time_deposit` 按参与者人数均摊)。
- XP:`docs/04 §8` 标注"分摊规则待定" → 采用**均摊**为默认,后续可配。
- 状态机:新增"部分完成"表达(现有状态机是单人单线程),待定稿细化为独立 issue。
