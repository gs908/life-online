## 0. 结论摘要

1. **LLM 只写叙事,任务实质由模板决定**。模型不产生工作量,也不产生数值。
   实例的 `description` 保持模板原文,叙事只写入 `lore_snippet`。
   这样模型在结构上没有能力改动孩子的实际工作量。
2. **生成发生在半夜的批量作业里**。生成时机是既有的 00:10 作业
   (`generate_daily_instances`),不在孩子打开 App 时调用 LLM。
3. **默认不审核**。内容安全靠提示词约束保证。审核开关作为后续阶段(P3),
   默认关闭。
4. **不引入变体池,也不引入缓存**。实例行本身就是内容的唯一载体。
   幂等由既有的部分唯一索引 `uq_scn_task_instance_template_generated_for_date` 保证。
   原因:预生成池是缓存,缓存必须随输入变化作废;而难度递进要求临期决策,
   与预生成在原理上冲突。详见 §12 的说明。
5. **LLM 失败不得影响实例创建**。失败时回落模板文本,并标记 `FALLBACK`。

## 1. 目标与术语

**目标**:每个任务实例带一段简短故事文本。故事文本贴合当前赛季主题。
故事文本不改变任务实质。

| 术语 | 含义 |
|---|---|
| 模板 | `scn_task_template` 的一行。它保存任务规则与任务实质。 |
| 实例 | `scn_task_instance` 的一行。它是某个孩子某一天的一个任务。 |
| 任务要点 | 任务实质中不变的部分。例:"口算 4 页,100 以内"。字段 `content_brief`。 |
| 叙事 | 故事文本。它只交代场景,不是任务指令。 |
| 生成器 | `server/app/services/task_generator_service.py`。 |
| 批量作业 | `generate_daily_instances` 作业。每天 00:10 运行,时区 Asia/Shanghai。 |

## 5. 数据变更

- **R1.** 给 `scn_task_template` 增加 `content_mode` 列。类型 `VARCHAR(16)`。
  非空。默认 `STATIC`。取值 `STATIC`、`LLM`。
- **R2.** 给 `scn_task_template` 增加 `content_brief` 列。类型 `TEXT`。可空。
- **R3.** 给 `scn_task_instance` 增加 `content_source` 列。类型 `VARCHAR(16)`。
  非空。默认 `TEMPLATE`。取值 `TEMPLATE`、`LLM`、`FALLBACK`。
- **R4.** 给 `scn_task_instance` 增加 `generation_meta` 列。类型 `JSON`。可空。
- **R5.** 产出 1 个迁移。`down_revision` 设为 `b7e4d9f2a6c1`。
  全部新列必须只增不改(expand-only)。存量行必须保留原有数据。

## 6. 生成器行为

- **R6.** 生成器必须在创建实例时读取 `content_mode`。
- **R7.** `content_mode` 为 `STATIC` 时,生成器必须把模板的 `lore_snippet`
  复制到实例。生成器必须把 `content_source` 置为 `TEMPLATE`。
- **R8.** `content_mode` 为 `LLM` 时,生成器必须为每个新实例调用 1 次 LLM。
  生成器必须把叙事写入实例的 `lore_snippet`。
- **R9.** 生成器不要改 `title`、`description`、`xp_reward`、`time_deposit`、
  `expire_at`。任务实质必须保持不变。
- **R10.** 生成器必须在写库之前调用 LLM。生成器必须把叙事保存为普通字符串。
  原因:回滚会让会话内全部 ORM 对象失效。见 `task_generator_service.py:217-231` 的注释。
- **R11.** 以下路径不要调用 LLM:`rolled_forward`、`exists`、`kept`、
  `not_due`、`skipped_expired`。顺延的任务必须保留首次生成的叙事。
- **R12.** LLM 失败时,生成器必须复制模板的 `lore_snippet`,并把
  `content_source` 置为 `FALLBACK`。失败情形包括:能力未启用、能力未配置、
  HTTP 错误、超时、返回非法 JSON、返回空文本、文本超长。
- **R13.** 生成器不要向上抛 LLM 错误。实例创建必须始终成功。
- **R14.** `LLM` 与 `FALLBACK` 两种结果都必须写 `generation_meta`。
  内容:模型名、提示词哈希、token 数、耗时(毫秒)、`FALLBACK` 时的错误类名。

## 7. 提示词要求

- **R15.** 在 `app/services/ai_service.py` 增加函数
  `generate_task_narrative(...)`。生成器必须调用这个函数。
  生成器不要 import `common.llm`。模块规则:业务层只使用 `ai_service`。
- **R16.** 使用 `client.chat_json`,JSON schema 为
  `{"type":"object","properties":{"narrative":{"type":"string"}},"required":["narrative"]}`。
  `temperature` 设为 0.8。
- **R17.** system 提示词必须包含以下规则:
  - 你为家庭任务游戏写一段简短的故事文本。
  - 故事文本必须贴合当前赛季主题。
  - 不要改变任务。不要增加工作量。不要减少工作量。
  - 不要写数字、数量、页数、分钟数、奖励、难度。
  - 不要写任务指令。
  - 使用简体中文。
  - 长度 40 到 120 字。
  - 不要出现暴力、恐惧、恋爱、政治、宗教、医疗断言。
  - 不要出现个人信息。不要出现孩子姓名。
  - 主题为空时,写一段通用冒险场景。
- **R18.** user 消息必须包含:任务要点、赛季主题、分类、孩子等级、
  日期类型(工作日或周末)、任务类型。
- **R19.** `content_brief` 为空时,生成器必须用 `description` 作为任务要点。

## 8. 配置

- **R20.** 在 `config.yaml` 与 `app/config.py` 增加 `task_content` 段。
  键:`llm_enabled`(bool,默认 `true`)、`llm_timeout_seconds`(int,默认 `15`)、
  `max_narrative_chars`(int,默认 `200`)。
- **R21.** `llm_enabled` 为 `false` 时,生成器不要调用 LLM,并把
  `content_source` 置为 `FALLBACK`。原因:运维能看出模板要求的是 `LLM`。
- **R22.** 超时必须作用于每一次 LLM 调用。本阶段批量作业必须保持串行。
- **R23.** 叙事长度超过 `max_narrative_chars` 时,生成器必须按失败处理。

## 11. 测试与验收

- **T1.** `content_mode=STATIC`:实例保留模板的 `lore_snippet`。
  `content_source` 为 `TEMPLATE`。LLM 未被调用(用假客户端统计调用次数)。
- **T2.** `content_mode=LLM` 且 LLM 正常返回:`lore_snippet` 保存叙事。
  `content_source` 为 `LLM`。`title`、`description`、`xp_reward`、
  `time_deposit` 与模板一致。
- **T3.** `content_mode=LLM` 且 LLM 报错:实例仍然创建。
  `lore_snippet` 等于模板文本。`content_source` 为 `FALLBACK`。
  不向外抛异常。统计中 `fallback=1`。
- **T4.** `content_mode=LLM` 且返回文本超长:结果为 `FALLBACK`。
- **T5.** 同一天运行批量作业两次:只产生 1 条实例。LLM 调用次数为 1。
- **T6.** `roll_forward` 路径:LLM 未被调用。叙事不变。
- **T7.** LLM 能力关闭:全部实例仍然创建。`content_source` 为 `FALLBACK`。
  作业不失败。
- **T8.** 迁移可升级也可回滚。存量行取得默认值。

**验收标准**:全部测试通过。批量作业保持逐模板隔离。
单个模板失败不阻断其他模板。

## 12. 后续阶段(仅大纲)

**P2 — 难度递进。** 新增 `scn_task_template_progress` 表,字段:
`template_id`、`child_id`、`current_difficulty`、`streak`、`total_completed`、
`last_settled_on`。在结算时更新:审批通过时 `streak` 加 1;
过期或放弃时 `streak` 归零。连续 N 次正常结算后 `current_difficulty` 加 1,上限 5。
**重要**:必须先给 `scn_task_instance` 增加 `difficulty` 与 `estimated_minutes`
两个快照列。原因:XP 在审批时从**模板**读取难度。见 `task_service.py:680`。
没有快照时,后续改动模板会移动未结算任务的 XP。

**P3 — 内容审核开关。** 给 `scn_task_template` 增加
`content_review_required` 列,默认 `false`。新增 `scn_task_content_draft` 表,
字段:`template_id`、`target_date`、`narrative`、`status`、
`reviewer_account_id`、`reviewed_at`。新增前瞻作业,为次日生成草稿。
生成器使用目标日期的 `APPROVED` 草稿。
**重要**:没有已批准的草稿时,生成器必须使用模板文本。
任务板不能为空。

**P4 — 里程碑触发。** 给 `scn_task_template_trigger` 增加 `MILESTONE` 种类
与 `params` JSON 列。参数示例:`{"after_streak": 5, "of_template_id": "..."}`。
消费点是审批路径,不是日历作业。限时挑战使用现成的
`timed_mode=DURATION` 字段表达。

**不要改动**接口 `POST /scn/ai/generate-quest`。它保留给家长手工使用。

## 13. 为什么不预生成变体池

预生成一批叙事备用,本质是缓存。缓存必须有一个失效键。
失效键要覆盖全部决定内容的输入:任务要点、赛季主题、难度、孩子等级、任务类型。
任何一个输入变化,旧内容即作废。因此:

1. **新鲜度**:按需生成在下一个实例上自动反映最新主题与等级。预生成会滞后。
2. **难度递进**:明天的难度取决于最近几天的结算结果。
   预生成的内容不可能反映这些结果。两者在原理上冲突。
3. **成本**:一条内容只用一次时,预生成不省 token,只改变生成时间。
   一条内容重复使用时,孩子每天看到相同内容,与"每天不一样"的目标冲突。
4. **性能**:00:10 是批量作业,延迟不敏感。按需生成没有性能代价。

只有以下情形才值得引入预生成:内容必须人工预审,或 LLM 在生成窗口内不可用。
第二种情形用"重试 + 静态回落"即可解决。第一种情形见 §12 的 P3。
